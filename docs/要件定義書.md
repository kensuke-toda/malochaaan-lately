## 1. プロダクト概要

**Lately** は、Ken とパートナーの2人で運用する近況報告サイト。買ってよかったモノ（Things）と日々の出来事（Diary）を、なるべく手間なく記録・公開することを目的とする。

- **主用途**: 2人の記録＋知人に「最近何してるか」を見せる公開ページ
- **ユーザーモデル（🚧 方針変更）**: Ken・パートナーの2アカウント。**1つの公開ページを2人で共有**し、それぞれが自分のアカウントでログインして投稿する（`my-app`のhousehold型に近い、専用の家庭グループ概念は持たない固定2アカウント運用）。投稿には誰が書いたかが分かるよう投稿者名を表示する
- **公開範囲**: トップページ・詳細ページ（Things・Diary共に）は誰でも閲覧可能（読み取り全公開）。投稿・編集は各自のログイン後のみ可能

### やらないこと（明確な非スコープ）

- 3人以上のユーザー対応、オープンなサインアップ（アカウントは2人分のみ、Ken自身が発行）
- コメント機能・いいね機能などのソーシャル要素
- Places（3Dジオラマ演出）、Books/Sounds/Posts/Worksセクション（将来検討、Phase 3以降）

## 4. 機能仕様

### 4.1 認証（管理画面）※方針変更中

**現行実装（変更前）**: Supabase Authは使わず、環境変数 `ADMIN_PASSWORD` と一致するパスワードでログイン。`lately_admin_session` Cookie（パスワードのSHA-256ハッシュ）で認証状態を管理。

**新方針（実装予定）**:

- Supabase Authのメール＋パスワード認証を使用。アカウントは2つのみ（Ken・パートナー）で、オープンなサインアップは提供しない（Ken自身がSupabase側で2アカウントを作成する運用を想定）
- `profiles` テーブル（`id` は `auth.users.id` と1:1、`display_name` を持つ）を新設し、投稿者の表示名を解決する
- `things` / `diary_entries` に `created_by`（`auth.users.id`）カラムを追加し、誰の投稿か記録する
- ログイン後の `/admin` はどちらのアカウントでもモノ・日記の追加ができる。**編集・削除は自分の投稿のみ**か、**どちらの投稿も編集可**かは要件次第（→ [WBS](./WBS.md) で確定）
- RLS: `select` は引き続き全公開。`insert` は認証済みユーザーのみ（`created_by = auth.uid()` を強制）。`update`/`delete` の権限範囲は未決事項（§9参照）
- 公開ページ（トップ・詳細）で投稿者の表示名を表示する

この変更に伴い、既存の `ADMIN_PASSWORD` ベースの実装（`src/lib/admin-auth.ts`）は撤去し、Supabase Authのセッション管理に置き換える。

### 4.2 Things（モノ図鑑）

**データ項目**

| 項目 | 必須 | 内容 |
|------|------|------|
| 商品名 (`name`) | ○ | |
| ブランド名 (`brand`) | × | |
| 商品ページURL (`product_url`) | × | クリックで外部遷移 |
| 元画像 (`original_image_url`) | × | 管理画面からアップロード、`things-images` バケットに保存 |
| 透過済み画像 (`processed_image_url`) | × | **Phase 1では自動生成しない**。用意できる場合は事前に加工した画像をアップロードする運用でカバー |
| メモ (`memo`) | × | |
| 並び順 (`sort_order`) | × | デフォルト0（将来の手動並び替え用。Phase 1のUIからは変更不可） |

**表示ロジック**: `processed_image_url` があればそれを、無ければ `original_image_url` を表示する。

**操作**: 管理画面から追加（フォーム一括）・削除（一覧から即削除、確認ダイアログなし）。編集機能はPhase 1では未実装（削除して追加し直す運用）。

### 4.3 Diary（日記）

**データ項目**

| 項目 | 必須 | 内容 |
|------|------|------|
| タイトル (`title`) | ○ | |
| 本文 (`body`) | × | 複数行テキスト |
| 日付 (`entry_date`) | × | 未指定時は今日の日付 |
| 写真 (複数、`diary_photos`) | × | 複数ファイル選択でまとめてアップロード、`diary-images` バケットに保存。`sort_order`はアップロード順 |

**操作**: 管理画面から追加（タイトル・本文・日付・複数写真を1フォームで）・削除（紐づく `diary_photos` もCASCADE削除）。編集機能はPhase 1では未実装。

### 4.4 公開ページの表示ロジック

- トップページ: `things` を `sort_order`昇順→`created_at`降順で最大24件、`diary_entries` を `entry_date`降順で最大10件（写真同時取得）
- 詳細ページ: `id` 指定で1件取得、存在しなければ404 (`notFound()`)
- Supabase未設定（環境変数がプレースホルダーのまま）の場合、公開ページはエラーにせず「Supabaseが未設定です」という案内を表示し、詳細ページは404を返す

## 5. 技術アーキテクチャ

```
[ブラウザ（公開ページ / 管理画面）]
        │
        ▼
[Next.js (App Router) + TypeScript]  ── Vercel にデプロイ予定
   │
   ├── Server Components: 公開ページの読み取り（anonキー、RLSに従う）
   ├── Server Actions (/admin/actions.ts): 書き込み（Service Roleキー、RLSを迂回）
   │
   ▼
[Supabase]
   Database（things / diary_entries / diary_photos）+ RLS
   Storage（things-images / diary-images、公開読み取りバケット）
```

| 層 | 技術 |
|----|------|
| フロントエンド | Next.js (App Router), React, TypeScript, Tailwind CSS |
| バックエンド/DB | Supabase（Database, Storage）※Authは不使用 |
| ホスティング | Vercel（Hobbyプラン、無料枠） |
| 画像表示 | `next/image` は使わず素の `<img>` タグ（remotePatterns設定を省略するため） |

### 主要ソースマップ

| パス | 役割 |
|------|------|
| `src/app/page.tsx` | トップページ |
| `src/app/things/[id]/page.tsx` | モノ詳細 |
| `src/app/diary/[id]/page.tsx` | 日記詳細 |
| `src/app/admin/page.tsx` | 管理画面（ログイン＋フォーム＋一覧） |
| `src/app/admin/actions.ts` | 管理画面のServer Actions（ログイン/ログアウト/CRUD） |
| `src/lib/admin-auth.ts` | パスワード認証・セッションCookie管理 |
| `src/lib/supabase/server.ts` | 公開ページ用（anonキー、読み取り専用） |
| `src/lib/supabase/admin.ts` | 管理操作用（Service Roleキー、RLS迂回） |
| `src/lib/supabase/config.ts` | Supabase設定有無の判定 |
| `src/types/index.ts` | `Thing` / `DiaryEntry` / `DiaryPhoto` 型定義 |
| `supabase/schema.sql` | DBスキーマ・RLSポリシー・Storageバケット定義 |

| 変数名 | 用途 |

## 6. データモデル

現行スキーマ（実装済、`supabase/schema.sql`）:

```
things
  id (uuid, PK)
  name (text, not null)
  brand (text, null可)
  product_url (text, null可)
  original_image_url (text, null可)
  processed_image_url (text, null可)
  memo (text, null可)
  sort_order (integer, default 0)
  created_at (timestamptz, default now())

diary_entries
  id (uuid, PK)
  title (text, not null)
  body (text, null可)
  entry_date (date, default current_date)
  created_at (timestamptz, default now())

diary_photos
  id (uuid, PK)
  diary_entry_id (uuid, FK -> diary_entries.id, on delete cascade)
  image_url (text, not null)
  sort_order (integer, default 0)
```

**🚧 方針変更後に追加予定**:

```
profiles
  id (uuid, PK, FK -> auth.users.id)
  display_name (text, not null)

things.created_by      (uuid, FK -> auth.users.id, not null)
diary_entries.created_by (uuid, FK -> auth.users.id, not null)
```

**RLS方針（変更前）**: 3テーブルとも `select` は全公開（`using (true)`）。`insert`/`update`/`delete` のポリシーは意図的に作成せず、Service Roleクライアント（RLSを迂回）のみが書き込み可能。

**RLS方針（変更後・予定）**: `select` は引き続き全公開。`insert` は認証済みユーザーが `created_by = auth.uid()` で自分の投稿として作成。`update`/`delete` の範囲（自分の投稿のみ／どちらの投稿も可）は未決（§9）。

**Storage**: `things-images` / `diary-images` の2バケット、どちらも `public: true`（読み取り公開）。書き込みは変更前はService Role経由のみ、変更後は認証済みユーザーからの直接アップロードに変える想定（Storageポリシーの追加が必要）。

## 7. 受け入れ条件（Phase 1）

1. `supabase/schema.sql` を実行したSupabaseプロジェクトに接続すると、トップページでThings/Diaryが表示される
2. `/admin` に正しいパスワードでログインできる。誤ったパスワードではログインできない
3. 管理画面から画像付きでモノを追加すると、`things-images` バケットにアップロードされ、トップページに反映される
4. 管理画面から複数写真付きで日記を追加すると、`diary-images` バケットにアップロードされ、詳細ページで全て表示される
5. 管理画面から削除すると、一覧・トップページ・詳細ページから消える（日記削除時は紐づく写真レコードも消える）
6. 未ログイン状態で `/admin` を直接開いてもフォームは表示されない（ログイン画面のみ）
7. Supabase未設定の状態でも、トップページ・管理画面はエラー画面にならず、案内メッセージが表示される
