## 0. 運用ルール（必読）

### 状態は4段階。担当者ごとに動かせる範囲が決まっている

| 状態 | 動かせる人 | 意味 |
|------|-----------|------|
| 未着手 | PM（Ken） | まだ手をつけていない。優先度づけ・並び順はPMの権限 |
| 進行中 | エンジニア（AI/Cursor） | 着手した |
| **実装完了（レビュー待ち）** | エンジニア（AI/Cursor） | コードは書けた・ビルド/動作確認は自分でOK。**PMの検収はまだ** |
| **検収完了** | PM（Ken） | 「受け入れ条件」列に書かれた基準と1件ずつ照合してOK。**この列を動かせるのはPMだけ** |

エンジニア（AI）が「検収完了」を自分で付けることは禁止。実装完了までがAIの権限。

### GitHub上での操作対応表（非エンジニア向け・覚えることはこれだけ）

GitHubのラベルを毎回選ぶのは面倒なので、実際の運用は**ボードの列**と**Issueの開閉**の2つだけで表現する。

| WBSの状態 | GitHub Project boardでの見え方 | Issueの状態 |
|---|---|---|
| 未着手 | 「Todo」列 | Open |
| 進行中 | 「In Progress」列 | Open |
| 実装完了（レビュー待ち） | 「Done」列 | **Open**（まだ閉じていない＝PM未確認のサイン） |
| 検収完了 | 「Done」列 | **Closed**（PMが閉じた＝これが唯一の「本当に終わった」印） |

→ **PMが覚えることは「Doneに来ているけどまだ開いてるIssueを、中身を確認してから閉じる」これだけ**。閉じる＝検収完了。

### 行の追加・削除・優先度変更はPMの権限

エンジニアはタスクの分解案を提案できるが、スコープの追加・削除・優先度の確定はPMが行う。

### 完全性チェックのやり方（項目漏れ対策）

新しいタスクを思いつきで追加しない。**要件定義書の各セクションと本WBSを見比べて、要件定義書に書かれているのにWBSに無い項目がないか**を都度チェックする（逆に、要件定義書に根拠のないWBS行があれば、それはスコープ外の増殖なので要件定義書側に追記するか行を消す）。

## GitHub Issues / Projectsとの同期方法

- **Issues**: https://github.com/kensuke-toda/malochaaan-lately/issues （G0〜G10。G8=#9, G9=#10, G10=#11。Milestone: `Phase 1: 方針変更対応（マルチユーザー化）`）

- 本ファイルの各グループ（G1〜G7）を1つのGitHub Issueとして作成し、行（ID）をIssue本文のチェックリストにする
- Issueのラベルで状態を表現: `status:not-started` / `status:in-progress` / `status:dev-done` / `status:accepted`
- **状態変更のたびに、このファイルとGitHub Issue側の両方を更新する**（本ファイルが正本、Issueは視認性のためのミラー）
- 検収完了（`status:accepted`）にラベルを付け替えられるのはPMのみ、という運用ルールをIssue側にも明記する
